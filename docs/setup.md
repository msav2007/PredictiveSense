# Setup - fresh clone to a running system, on CPU or NVIDIA

This is the bootstrap for a machine that has just `git clone`d the repo. The
same codebase runs on the CPU-only laptop and on an NVIDIA laptop with **no
architectural change** - only which optional dependency extra you install and
what `perception.provider` resolves to.

## What a fresh clone actually contains

Verified by inspection of `.gitignore`:

- **Source, configs, docs, tests** - all present.
- **`models/manifest.json` + `models/registry.json`** - present (git-ignore
  exceptions). The **`.onnx` weight files are NOT** - `models/*.onnx` is
  git-ignored. You must run `scripts/fetch_models.py` (below).
- **`data/`** - empty. `data/**` is git-ignored: no recorded clips
  (`data/raw/`), no evaluation frames or labels (`data/eval/`), no object
  samples (`data/objects/`). The app runs without them; the evaluation harness
  and the Object Learning Studio need data the developer collects.
- **`results/`** - only `test_set_openings.md` and `model_comparison.md` are
  tracked; everything else is regenerated by the benchmark / eval scripts.
- **`.venv/`** - not present; you create it.
- A **git remote** is configured (`origin`). If yours is not, that only affects
  `git pull`; it does not affect the steps below.

## Python

Python **3.11** (the project pins `>=3.11,<3.12`). Check: `python --version`.

## 1. Virtual environment

```bat
python -m venv .venv
.venv\Scripts\activate            REM  Windows
REM  source .venv/bin/activate    REM  macOS / Linux
python -m pip install -U pip
```

## 2. Install - pick EXACTLY ONE ONNX Runtime extra

`onnxruntime`, `onnxruntime-gpu` and `onnxruntime-directml` install the **same
module name** and cannot coexist in one environment. `pyproject.toml` expresses
this as two mutually exclusive extras:

| Machine | Command | Execution provider |
|---|---|---|
| CPU-only laptop / CI (the default) | `pip install -e ".[cpu,dev,camera]"` | `CPUExecutionProvider` |
| NVIDIA laptop | `pip install -e ".[cuda,dev]"` | `CUDAExecutionProvider` (+ CPU fallback) |

- `[cpu]` = `onnxruntime==1.24.4`. **The CPU environment never pulls a GPU
  package**, and the full test suite must pass here.
- `[cuda]` = `onnxruntime-gpu==1.24.4`. It also ships `CPUExecutionProvider`, so
  `provider: cpu` still works from a `[cuda]` environment.
- `[camera]` = `pygrabber` for human-readable DirectShow camera names (Windows,
  optional).
- `[dev]` = `pytest`, `httpx`, `playwright` (browser tests). Run
  `playwright install chromium` once if you want the `browser`-marked tests.

If you run a bare `pip install -e .` (no extra) you get **no ONNX Runtime** and
perception will not load - that is deliberate, so the CPU env cannot
accidentally drag in a GPU wheel. Always name an extra.

### CUDA version coupling (NVIDIA only)

`onnxruntime-gpu==1.24.4`'s CUDA execution provider requires a matching CUDA and
cuDNN **runtime**:

- **CUDA 12.x** (12.2-12.6 tested by the ORT project for the 1.24 line)
- **cuDNN 9.x**

Check what you have: `nvcc --version` (or `nvidia-smi` for the driver's max CUDA)
and the cuDNN version in your CUDA `bin`/`lib`. A mismatch does **not** raise a
clean error by itself - the CUDA EP just fails to appear in
`onnxruntime.get_available_providers()`. This project turns that into a clear
diagnostic: `perception.provider: cuda` with the EP absent raises
`ProviderUnavailableError` naming the fix, and if the EP is present but the
session still initialises on CPU the loop raises a `RuntimeError` naming the
likely CUDA/cuDNN mismatch (`perception/runtime.py`).

## 3. Fetch the model weights (one-time, needs network)

```bat
python scripts\fetch_models.py
```

Downloads `yolo11n.onnx`, `yolo11n-pose.onnx` and `yolox_tiny.onnx` from their
GitHub release assets, verifies each SHA-256 against `models/manifest.json`
(refuses to use a file on mismatch), and writes `models/LICENSE-AGPL-3.0.txt`
beside the YOLO11 weights. **Runtime makes no network call** - this is a setup
script only. Without the weights the app still starts but runs *without*
perception (empty detections/poses) and `models`-marked tests skip cleanly.

## 4. Select and confirm the provider

`perception.provider` in `config/profiles/dev.yaml` / `eval.yaml` is **`auto`**
(never hard-coded). `auto` tries `cuda -> directml -> cpu` and takes the first
whose EP is present, always falling back to CPU, and logs the choice:

```
perception engine: detection=True pose=True provider(config=auto -> cuda) pose_cadence=every_n:2
perception session yolo11n.onnx: provider requested=cuda active=CUDAExecutionProvider ...
```

Force a specific one by editing the profile: `provider: cpu` | `cuda` |
`directml`. An explicitly named provider whose EP is absent is a **loud
failure** with an actionable message - it never silently falls back to CPU.

Confirm which provider is **actually live** (not what config asked for) in any
of these places:

- the startup log lines above (`active=...`);
- **Diagnostics panel** in the dashboard - the "active EP" row;
- `GET /api/runtime` -> `{"active_provider": "...", "model_version": "...", "available_providers": [...], "machine": {...}}`;
- the session manifest `results/session_<id>.json` -> `extra.perception.active_provider` and `extra.machine`;
- every benchmark result file carries the EP in use and a machine fingerprint.

## 5. Run

```bat
python scripts\run_app.py --profile dev --source-kind browser
```

Open <http://127.0.0.1:8000>, allow the camera. The `<video>` preview is native;
analysis frames go over `WS /ws/ingest`; the overlay is drawn on `/ws/state`
snapshots.

Backend-owned camera instead of the browser:
`python scripts\run_app.py --profile dev --source-kind device` (sets
`capture.owner: backend`).

## 6. Tests

```bat
pytest -q                 REM  full suite - must be green on a CPU-only machine
pytest -q -m models       REM  needs the fetched weights
pytest -q -m browser      REM  needs `playwright install chromium`
pytest -q -m cuda         REM  skips cleanly without CUDA; runs on the NVIDIA box
```

## Does a fresh clone currently produce a working install?

**Yes, on this documented path** (`clone -> venv -> pip install -e ".[cpu,dev]"
-> fetch_models -> run_app`). The one change from earlier phases: you must now
name an ONNX Runtime extra (`[cpu]` or `[cuda]`) - `pip install -e ".[dev]"`
alone no longer installs ONNX Runtime, by design (the CPU env must not be able
to pull a GPU wheel). The NVIDIA path (`[cuda]`) is documented and the provider
selection / loud-failure / active-provider-reporting code is implemented and
unit-tested, but has **not been executed on real NVIDIA hardware from this
environment** - that is the developer's physical verification (phase 8 report,
Part 2).
